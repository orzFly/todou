## Fixed

- **An IdP that accepts only `client_secret_basic` can be logged into.** todou
  sent `client_secret_post` on every code exchange and never read
  `token_endpoint_auth_methods_supported`. The method is negotiated per request
  now: post when the declaration offers it, basic when that is the only one of
  the two offered, post when it names nothing todou implements.
  `auth.oidc.token_endpoint_auth_method` (env
  `TODOU_AUTH_OIDC_TOKEN_ENDPOINT_AUTH_METHOD`, refused at startup when
  misspelled) overrides the negotiation for an IdP whose declaration disagrees
  with what it accepts. Worked example in `docs/deploy.md`.
- **Screens stop saying what they already show** — settings, search help, trash
  view, several dialogs. One deleted line was false: project settings promised
  that existing text keeps parsing under the reference format it was written
  under. References are resolved when submitted and stored as links, so nothing
  is ever re-parsed.

## Breaking changes

**One class of `oidc` deployment stops logging in**: an IdP declaring only
`client_secret_basic` while accepting only post, which worked while todou
ignored the declaration. Set `token_endpoint_auth_method =
"client_secret_post"`. Nothing catches this at startup, and the failure is
`exchange_failed` with the IdP's 401 `invalid_client` in the log —
indistinguishable from a wrong `client_secret`, which is why todou does not
retry with the other method.

Nothing else was removed or renamed.

## Upgrading

1. **Server only, no migration.** The web UI ships with the server; the API is
   untouched, so either CLI pairs with either server as before.
2. **`oidc`: read your IdP's declaration first** —
   `token_endpoint_auth_methods_supported` in its discovery document. Offering
   `client_secret_basic` and not post is the case that moves: todou sends basic
   now, so set the override if the IdP's client is really set to post. Post
   offered, list empty, field absent: nothing changes.
3. **`single` and `forward`: nothing to do.**
