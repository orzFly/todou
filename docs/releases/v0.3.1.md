## What's new

- **A prefixed positional names its project** — `todou issue view A-1`
  resolves the prefix rather than taking the number off it, by the same
  priority the renderer uses: this project's own prefix first, then the
  cross-project directory when exactly one project you can read holds the
  prefix. A ref pasted out of another project opens that project's card.
- **Every refusal carries the spelling that works** — a prefix nobody holds
  lists the ones within reach and suggests a near miss; a prefix several
  projects hold prints `bravo/1 or charlie/1`; an autolink prefix says it
  points outside todou and shows the external URL it resolves to. Each exits
  1, and does so before any issue is fetched.
- **`-p/--project` is a fence, not a hint** — a positional whose prefix names
  a different project is refused rather than followed, so a pasted ref cannot
  quietly redirect a command aimed at a sandbox. `TODOU_PROJECT`,
  `.todou.toml` and the git binding are still overridden without comment,
  exactly as `slug/76` has always overridden them.
- **`slug/PREFIX-76` is checked too** — against the prefix that project
  writes now or wrote in the past, so a ref out of an old commit message
  still resolves while a mistyped one is caught instead of ignored.

## Breaking changes

**A prefix that doesn't resolve here now fails the command.** `PREFIX-N` used
to be read for its digits with the prefix discarded, so `todou issue view A-1
-p home` printed home's issue 1 and exited 0 no matter which project `A`
belongs to. It exits 1 now, and so does `home/FOO-1`, which used to mean
`home/1`.

Scripts that paste refs between projects are where this surfaces — they were
already getting the wrong card, silently. Three ways out, in order of
preference: write the qualified form (`alpha/1`), drop `-p` and let the
prefix resolve, or strip the prefix (`#1`) where the current project really
was meant.

Nothing else changed for callers: no endpoint or flag was removed, and `76`,
`#76`, `slug/76`, `slug#76` and a full issue URL all behave as before.

## Upgrading

1. **CLI only.** No server change and no migration; a 0.3.0 server serves a
   0.3.1 CLI unchanged, and an older CLI against it is unaffected.
2. **Redistribute the builds.** A deployment hands out the CLI it was made
   with at `GET /api/cli`, so machines keep the old resolution until a new
   drop is pushed and they pull again.
3. **How it degrades.** A project's reference config that cannot be read
   restores the pre-0.3.1 reading — prefix ignored, number taken as the
   current project's. An unreadable cross-project directory
   (`/me/reference-directory`, added in 0.3.0) instead reads as empty, so a
   foreign prefix is refused rather than guessed at.
