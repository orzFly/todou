## Fixed

- **Forward auth works through the batch gateway** — under `auth.mode =
  "forward"`, every sub-request of `POST /api/batch` answered 401. The gateway
  built them without the connection's peer address, leaving the
  `http.trusted_proxies` check with nothing to judge, and without the headers
  the proxy asserts the identity in. The web UI batches its reads, so a
  correctly configured deployment bounced to a login page blaming the proxy for
  a header it had in fact sent.
- **What was in scope** — `single` and `oidc` deployments never saw this, and a
  Bearer PAT authenticated in every mode throughout. Sub-requests still run the
  whole auth chain and are still judged on the real connection's peer; the
  identity headers they now repeat come from an envelope the proxy had already
  sanitised.

## Breaking changes

None.

## Upgrading

- **Server only.** No migration, no configuration change. The web UI ships with
  the server, so the two move together, and a 0.4.0 CLI talks to a 0.4.1 server
  unchanged.
- **If you widened `http.trusted_proxies` while chasing this, narrow it back.**
  In forward mode that list is the only thing standing between the backend port
  and anyone who can send an identity header.
